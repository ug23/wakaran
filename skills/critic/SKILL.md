# /critic

「このやり方で本当にいいのか」と感じた時点で打つ。
同じセッションの中で自分の案を採点しても、同じ前提を同じ順で読むので同じ見落としを引き継ぐ。
批評は、会話を持たない別のエージェントに、ファイル1本だけを渡して行う。

## 引数

- なし: 手順1で検討状態をファイルに落としてから批評する
- ファイルパス: そのファイルを批評対象にする（手順1を省略）

## 手順

### 1. 検討状態をファイルに落とす
- 置き場は、プロジェクトの CLAUDE.md に決定ログや検討メモの置き場が書かれていればそこ。無ければ `docs/wakaran/`
- ファイル名は `YYYY-MM-DD-<題材>.md`。`/wakaran` の出力ファイルが同じ題材で存在すればそれに追記する
- 書く内容: 決めようとしていること、いまの案、その根拠、捨てた案とその理由、前提。すべての主張に [実測]/[読んだ]/[仮定] の印を付ける
- 会話では話したが文書に無い事実は、検出も批評もできない。判断に必要な項目や根拠が文書に無い場合だけ、その不在を抜けとして指摘できる

### 2. `wakaran:critic` agent に渡す
- 渡すのはファイルパスだけ。会話の要約や補足を添えない
- 必ず plugin のスコープ付き識別子 `wakaran:critic` を使う。同名の project/user agent は使わない
- agent の出力制約は定義側にある（矛盾・抜け・pitfall のみ、代案なし、各指摘に確認度と「無視した帰結」、1000字以内）

### 3. 採否を書く
- 返ってきた指摘を利用者に示す
- 利用者に聞くのは「どの指摘を受けるか」の1問だけ。指摘の技術的な正否を利用者に判定させない。正否が分からない指摘は「未判定」として残す
- 採否と未判定を、同じファイルの末尾に `## 批評と採否` の見出しで追記する

## やらないこと

- 批評の代わりに代案を出すこと
- 同じセッションで自分の案を採点すること
- 指摘の技術的な正否を利用者に判定させること
